Bloom · implementation reference · docs/design/

The rules a screen must hold before it reaches an operator.

Bloom already has tokens, presets, contrast tests and a written design system. What it does not have is a geometry contract: nothing in the builder, the seed files or the renderers knows how much room a widget's own content needs. So a gripper gets authored at 130×130, renders a title, a 56 px button and a 28-character topic string, and is cut — and no test fails.

This page is that contract. Every number below is derived from a file in the repo, not chosen: tokens from libs/ui/src/theme.ts, content heights from the renderers in libs/widget-renderers/src, geometry from backend/seed/applications.

01 Three bugs, one missing rule

These are not three unrelated defects. All three are the same absence: authored geometry is trusted, and content is never measured against it.

Observed · Drive, both robots

The gripper card is cut. drive-gripper is authored 130×130 with show_details: true. ToggleWidget renders three stacked rows — title, 56 px button, then the literal topic /gripper_controller/commands.

needs 250×144 · has 130×130

Observed · Drive, both robots

Pivot is shorter than Height. drive-rz is 130×260; drive-z is 130×440. Two controls of the same kind, on the same row, at different sizes — and 260 is below the vertical slider's own minimum, so the readout clips too.

needs 312 tall · has 260 · sibling has 440

Observed · Drive, Explorer

Speed readouts are cut mid-digit. drive-max-linear-speed is 210×130 and renders title + unit + a min → max range on one header line. At 210 px the range runs past the card edge.

needs 300×132 · has 210×130

R1

Every widget kind declares a minimum size, computed from what it actually renders in the configuration it is given. §07 is that table.

R2

A card grows rather than clips. The frame's content box gets min-height, not overflow: hidden. Clipping an operator control is never the correct failure.

R3

Siblings of one kind on one row share one size. Height and Pivot, Both and Jaco, the two speed limits. Asymmetry has to mean something.

R4

The builder warns, it does not block. Existing seeds stay valid; an undersized widget is flagged in the inspector and in the review checklist, with the required size offered as a one-tap fix.

What each colour is allowed to mean

02b The series ramp — the gap that made people name hexes

Invariant 02 says no feature file names a colour — and then the plot board needs eight distinguishable series and the token set has six semantic colours, none of which mean "the fifth thing on a chart". So people invent hexes. The fix is a token set for the need, not an exception to the rule.

How it is built

One hue rotation at roughly constant lightness, starting from forest and sage so the first two series are the product's own colours. Every entry sits between L* 40 and 62, so no series disappears on cream and none shouts.

Rules

Assign in order; never skip to pick a nicer colour. series-1 is the emphasised series where one exists — the manager output on Command sources. Series colour is never semantic: a red series does not mean a bad value.

Eight is the limit

Past eight overlaid series a plot is not readable and colour cannot carry the difference. The picker allows more; the ramp repeats with a dashed stroke and the design does not pretend that is legible.

03 Type — three faces, one floor
Cormorant Garamond

Display. Landing, builder card titles, empty states. Never inside a runtime app — an operator reading at arm's length does not need a serif.

Atkinson Hyperlegible

Everything a person must act on: widget titles, buttons, direction words, status, settings. Its disambiguated letterforms are the reason it is here, not the look.

JetBrains Mono

Machine values only: topics, frame ids, numeric readouts, payloads. If it is monospaced, it came from the robot or goes to the robot.

The target is physical. A canvas fit-scaled to 0.8 turns a 56 px button into 45 px of glass. The minimum-size table in §07 is stated at scale 1.0; the builder must report the effective size after fit, for the whole screen, not one selected widget.

05 The artboard — named regions for new screens

Authored at 1280×720, checked at 1024×600. The kiosk bar takes 44 px, leaving a 676 px body at native and 556 px at the small panel (ADR 0127). Free absolute placement stays supported for existing apps; new screens are composed from four named regions so that a control is in the same place on every screen of an app — the eyes-off requirement.

Artboard padding 14 px, region gap 12 px, card gap 12 px, in-card gap 8 px. Everything is a multiple of 2; nothing is a multiple of 5.

Control 14 px, card 18 px, pad 22 px, panel 26 px. Larger surface, larger radius — never the reverse.

06 Card anatomy — where the pixels go

Every widget card is the same five bands. The minimum size of a kind is the sum of the bands it renders — which is why show_details is a geometry setting, not a cosmetic one.

title + unit · 24
detail strip · 30 · only if show_details
control · kind minimum
readout · 28
topic · 18 · only if show_details
Padding 16, gaps 8

A card's fixed overhead is 32 (padding) + 24 (title) + 8 (gap) = 64 px before the control gets a single pixel. Add +28 for a readout, +56 for the detail strip and topic line.

The topic line sets the minimum width

A topic is rendered in 13 px mono and must not wrap or clip. /gripper_controller/commands is 28 characters ≈ 218 px, so the card cannot be narrower than 250 px. That single line is the whole gripper bug.

Better: don't render the topic at all

An operator cannot act on /gripper_controller/commands. Runtime default is show_details: false; the topic belongs in maintenance diagnostics and in Bloom Debug. §08.

06b The pad recipe — one formula, never a tuned number

A joystick pad has four direction labels, a dead-zone ring and a knob. Tuning those by eye per pad is how a design drifts: change the pad size and the four gaps stop matching, an arrow orphans onto its own line, and two pads side by side stop being the same square. Every number below is derived from one input — the pad's edge length S.

▲ Forward ▼ Back ◀ Left Right ▶ S = 300

The operator pad at S = 300. Gap 12 on all four sides, by construction rather than by measurement.

The formula
inset      =  8          label edge to pad edge
labelWidth = 64          fits "Right ▶" at the 17px floor
gap        = 12          label edge to ring, all four sides
lineHeight = 20

block      = inset + labelWidth            = 72
topInset   = block - lineHeight            = 52
ring       = S - 2 * (block + gap)         = S - 168
deadzone   = ring * 0.2                    the real 0.2 axis dead zone
knob       = S * 0.26
S 340
ring 172 · dz 34 · knob 88
S 376
ring 208 · dz 42 · knob 98
S 300
ring 132 · dz 26 · knob 78
Four rules that came from getting this wrong
  • Ring in px, never %. A percentage ring on a non-square box renders an ellipse, and the four gaps stop matching.
  • Arrow bound to its word with &nbsp;. The arrow carries the direction; orphaned on its own line it carries nothing, and the two sides end up different heights.
  • Pads in a pair are the same square. Set the pad flex: 0 0 auto so a flex parent cannot shave a pixel off one axis.
  • Pads in a row share a centre line. When one column has a trailing block (a Pivot slider), the other gets equal padding on its pad container — not a sibling spacer, which leaves a void and mis-centres by the flex gap.

The columns beside the pads get their declared minimum and nothing more — on the operator layout that is a 264 rail, a 106 Height slider and a 202 gripper column, which leaves 318 and 316 for the two pads. The pads are the reason the screen exists.

Interlocked and unsupported are different facts and must not share a treatment: interlocked means release the pads and you may; unsupported means this robot will never offer it. Opacity alone carries neither — both pair with a word.

Never dim a container

opacity on a card multiplies the contrast of everything inside it, including text that passes on its own. A 5.37:1 badge inside a card at opacity: 0.62 measures 2.45:1 — and nothing in the markup says so, which is why it survives review.

Dim the one element whose state it is, and only where the result still measures. For an unsupported or unavailable thing, use the treatment above instead: #f8f4eb fill, 2px dashed rgba(49,73,63,0.35), label at #536960 — 5.37:1, and it reads as unavailable rather than as faded.

10 Runtime chrome — the bar and the STOP
Explorer Manager Drive READY base_link 30 Hz Operator ⋯
The bar holds six things

App name, screen name, truthful link status, command frame, publish rate, profile, maintenance hold. Nothing else earns 44 px across the top of an operator's panel. The status chip describes the frontend-to-backend link and says so; it never implies the arm is reachable.

Gap in the build

Today the bar shows app, status, robot, frame and a hamburger. It is missing the screen name and the publish rate — the two things that tell an operator which screen they are on and that the tablet is still alive. The hamburger also reads as a menu; maintenance is a 1.5 s hold and should look like one, with the hold drawn as a fill.

In the build today
STOP

A white card with red text, the same weight as every widget around it. At a glance it is a label, not a control.

Specified · press to latch

Filled error, full-bleed in the status rail, the largest target on the screen. Press stops instantly; resuming is a one-second hold drawn as a fill. Try it.

Rules
  • STOP is chrome, never a widget. It cannot be moved, resized or removed by an app author.
  • Same corner on every screen of every app. Eyes-off means muscle memory.
  • Stopped: pads dim to 45% and go inert; mode and frame buttons stay live so the operator can prepare the resume.
  • Minimum 176×120 at scale 1.0, and it is exempt from fit-scaling below 64 px of glass.

Rule: control labels wrap to two lines and the control grows; they never shrink their type and never truncate. Authored labels — app, screen and widget titles — stay as written, because they are configuration data. Topics, frame ids, axes and numbers are never translated.

12 Builder — a different density, the same product

The builder is desktop, mouse-first, and dense. It is allowed 40 px targets, multi-column forms and hover affordances — but it uses the same tokens, the same type and the same card language, so an author never has to translate between the thing they are editing and the thing an operator will hold.

Canvas

The canvas is the operator's panel at true scale, on a #2a2f2c desk, with the device frame drawn around it. Three frames — 1024×600, 1280×720, 1820×720 — switch without leaving the screen. Panels never take space from it once editing starts.

Selection & overlap

Selected widget: 2 px forest outline plus a live size chip reading 400×440 · 56px glass. Overlapping interactive widgets get a petal wash and a named pair, immediately — not at publish time.

Undersize warning

Below the §07 minimum, the widget gets a pollen corner tag and the inspector offers Resize to 250×144 as one action. Authoring is never blocked; publishing surfaces it in the review checklist.

Libraries

App and screen cards use colour for grouping only — screen type, never status. Previews are on demand. Human names come before ids; an id is mono, small, and second.

Forms

Label above field, 40 px rows, 8 px radius, one column per concept. Destructive actions confirm inline with cancel/confirm — never window.confirm.

Review checklist

Geometry, touch bounds, overlap, command frame, topic policy — plus, now, minimum size and sibling symmetry. Each check names the widget and offers the fix. Export stays the last gate.

14 Cross-surface invariants — what must never diverge
01

A widget renders identically in builder and runtime. Runtime only removes editor affordances — it never resizes, reflows or restyles a widget.

02

Tokens come from libs/ui. No feature file names a colour. The three violations in §02 are the standing exceptions and are to be removed.

03

Colour never carries meaning alone. Every state in §09 pairs with a word, a border treatment, or both.

04

No surface claims more than it knows. "Requested", not "active"; link status, not robot status; simulated says simulated.

05

Adapter language stays out of operator surfaces. Frames and topics live in the bar, in maintenance and in debug.

06

A control is in the same place on every screen of an app. Moving STOP, the maintenance hold, or the status chip between screens is a defect.

ADR — when a rule constrains code

Minimum sizes, the 44 px bar, the region model, axis colour tokens. Same docs/decisions folder as architecture — ADR 0115, 0120 and 0127 already work this way.

Review log — when it is judgement

Why Pivot became 440 and not 360, why speed limits left the stage. Dated, one file per review, in the same shape as the UX handoff trace so the two read together.

The standard, briefly

Design lives where the thing it describes lives, and changes in the same pull request. A separate design repo guarantees drift; a design tool as source of truth guarantees two truths. Bloom's tokens are already code — keep the source of truth there and let this page render from them.
