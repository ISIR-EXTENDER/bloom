5a Runtime app library tablet · launching is choosing a role

All seven apps the runtime actually holds, as a list with a detail rail rather than a card grid — the grid ran out of room at four, and a library that silently hides three apps is worse than one that scrolls. One entry per app, not per device: the badge says which classes exist, the rail launches into a named profile.

Tap any row. Petanque admin carries the archived treatment from §09 — dashed, with the word, never a faded card. Bloom Debug is desktop-only. Four of the seven declare no profiles at all, so the rail says so instead of inventing roles for them.

The split pays off here

The joint table and the jacobian are what pushed Robot feedback over its tablet budget. At 724×440 each they are comfortable, and nothing had to be dropped.

40 px is earned

Desktop density applies because no operator profile can open Debug. The rule stays: the class sets the layout, the profile sets the floor.

Limit proximity

Each joint shows how close it is to its limit, coloured at 80 % and paired with the number — the thing you actually want to know when the arm stops moving.

STOP is still here

Debug can command the arm, so it carries STOP at the desktop minimum 420×140. A diagnostic screen that can move an arm without a stop is the worst screen in the product.

5c Device classes — decisions
Decided · separate apps, paired

explorer-manager and explorer-manager-desktop, authored independently, shown as one library entry with a device badge. Tablet authored 1280×720 and checked at 1024×600; desktop authored 1920×1080.

Decided · wrong device

Opens fit-scaled with a banner naming the class it was authored for and a one-tap switch to the sibling. Nothing is blocked; nothing pretends to be native.

Decided · density

The class sets the layout, the profile sets the target floor. A desktop operator with motor disabilities still gets 64 px; Debug gets 40 px because no operator profile can open it.

My call · the drift guard

You left this one to me. Separate apps means two copies of runtime_policy, action_presets and the allowlists per robot — four copies across Explorer and Kinova.

Shared by reference: both apps carry policy_id: "explorer" and the policy is defined once. Plus a CI check that a paired app's topics, frames and allowlists are identical. Drift in allowed_publish_topics is a safety property, and it is the one thing this split could quietly break.
